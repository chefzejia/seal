# 子系统 3：投标流程、台账与检查（`src/core/bid/`）

## 一、投标项目目录

```text
~/.seal/projects/<projectId>/       （同时是该 AI 会话的工作目录；SEAL_HOME 覆盖 ~/.seal）
  seal-project.json       项目信息：名称、截标日（YYYY-MM-DD，严格日历校验）、vaultId（可为空）、
                          招标文件清单（原件路径、副本路径、SHA256）、分册列表、创建时间
  tender/                 招标文件副本（含 .doc 转出的 .docx）
  materials/              用户补充的项目材料（报价单、产品资料等，可选）
  draft/<分册>.base.docx   复制时的基准稿（只读）
  draft/<分册>.docx        工作稿
  ledger.json             台账
  requirements.json       招标要求清单
  review/                 检查报告与渲染页
  final/<分册>.docx        终稿
```

- 一个项目可以有多个分册（如商务标、技术标）；工具以分册名寻址，只有一个分册时可省略。
- 项目可以不选知识库；无库模式下普通文本填充仍默认白底，核心商业敏感参数仍自动标黄，无法核实的资质/主体信息由 Agent 显式声明待定交人核对。
- 更换知识库或截标日后，与之相关的确认（见第三节的指纹）全部失效。

## 二、事实引用

文本值中可以写引用，由本模块在调用 Word 引擎前解析：

| 写法 | 含义 |
| :--- | :--- |
| `{{subject.<字段>}}` | 主体档案字段，如 `{{subject.creditCode}}` |
| `{{record:<id>.<字段>}}` | 证据记录字段，如 `{{record:yyzz-01.number}}` |
| `{{quote:<项目内相对路径>\|<原文片段>}}` | 招标文件或项目材料中的原文片段；Seal 校验该片段逐字出现在该文件的文字中 |

- 引用不存在的字段、记录或原文：拒绝整批编辑。
- 引用在截标日已过期、或持证主体为“禁用主体”“主体不符”的证据记录：拒绝。
- 引用“效期未知”“主体未知”的证据记录，或未核实的主体字段、记录：允许，写入内容自动待定（类别“待核对”）。
- 第三方资料只有在其持证方属于 `thirdPartyHolders`、且操作声明为第三方资料时才允许使用；插入时必须注明持证方。
- 插入证据记录的图片（`insert_image`，或 `insert` 中图片地址写成 `kb:<id>/<文件>` 的 Markdown 图片）同样适用以上规则。
- 经已核实引用写入的文字包进 `_Seal_F_<编号>` 范围（[子系统 2](2-word-engine.md) 第九节），台账 `fills` 按范围编号记录引用、解析值与核实状态。检查时比较范围内的当前文字与解析值：不一致即视为来源失效，按“待核对”处理（C05）。经未核实或效期、主体未知的引用写入的文字，直接作为“待核对”待定项包进 `_Seal_P_` 范围，同时记录引用来源。

## 三、待定项

- 定位：**信任 AI 整合与生成内容，只对极少数需要企业决策者拍板的敏感项与明确未核实的知识库引用标黄**；Seal 的核心职责是稳定 Office 格式、保护模板与确定性核验，而非给普通正文或常规表格涂满荧光黄。
- 类别：`报价`、`工期交期`、`质保`、`偏离`、`承诺`、`待核对`、`其他`。
- 待定项的来源：
  1. Agent 在操作中显式声明的 `pending`（仅用于需要人拍板的极少数商业决定、实质性负偏离、签署/印章日期或真实资料缺口；自拟段落中若仅有个别数值需拍板，用 `mark_pending` 局部标出该短语，不对整段整章批量挂 `pending`）；
  2. **敏感关键词加严（精准作用于字段/单元格，绝不连坐整行整章）**：`replace`、`set_cell`、`check` 与 `insert_rows` 写入时，仅检查**当前字段自身文字 + 所属列头（`r:0/c:j`）**（两列表格 `j=1` 且左侧 `c:0` 非空时**同时并入**左侧标签 `c:0`，保守不跳过列头，避免两列价格/交期/质保表漏标；非表格段落仅检查当前段落文字），命中核心商业参数关键词（`报价|总价|单价|合价|金额|税率|保证金|优惠`、`工期|交货期|交付期|交货时间|交付时间`、`质保|保修|维保`）时自动待定。`insert_rows` 按单元格独立判定，不因其他列连坐整行，且复制已标黄的模板行时先还原该格的原生高亮再独立判定；`insert` 插入的自拟章节**不触发**敏感词自动标黄；
  3. **引用未核实的知识库事实或图片**（第二节规定）：引用未核实、效期未知或主体未知的 KB 字段、证据记录或图片时自动待定为“待核对”（`source: 'unverified'`）；常规非敏感格式文字填写与表格行扩展不再因“未使用 `{{subject.*}}`/`{{record:*}}` 引用”而自动判为“格式填写的来源未核实”。
- Agent 不能确认、删除或降级待定项。
- **身份在文档里**：每个待定项对应草稿中的一个 `_Seal_P_<编号>` 范围，台账按编号记录类别、说明、来源、状态与确认，不按地址或偏移量追踪。编辑落在范围之内（含整体重写该范围）时，编号不变、内容更新，原确认失效；编辑完整覆盖并超出范围时，范围随之移除，台账将该项记为 `removed`，新写入的文字按本节重新判定待定；部分交叉的编辑被拒绝（子系统 2 第五节）。
- 人在工作台确认时记录指纹：分册名、范围编号、范围内的当前文字、类别，以及事实类待定项的 vaultId 与截标日。之后任何一项变化，确认自动失效，待定项重新打开，Word 中的黄标恢复。
- 工作台支持批量确认（如“确认本类全部”），但每一项单独记录指纹。

## 四、台账（`ledger.json`）

- 格式标识 `seal-ledger-1`，只由本模块的函数写入。
- `fills`：`_Seal_F_` 范围编号 → 分册、操作类型、引用、解析值与核实状态。
- `pending`：`_Seal_P_` 范围编号 → 分册、类别、说明、来源、状态（`open`、`confirmed`、`removed`）与确认记录。
- `dismissals`：对疑似空白的跳过记录，键为“分册 + 块地址 + 块文字 SHA256 + 提示文字 + 块内序号”，附理由与操作者（`agent` 或 `human`）；人对 Agent 跳过的过目也记在这里。块的文字一旦改变，该块的跳过与过目记录全部失效，提示重新出现。疑似空白本身不入台账。
- `acceptedChanges`：人接受的差异编号（见子系统 2 第七节）。
- `requirements`：人对招标要求覆盖情况的确认。
- `drafts`：每个分册最近一次由 Seal 写入时的 SHA256。

项目目录同时是会话工作目录，Agent 的通用文件工具也能触及其中的文件，因此：

- **项目外权威锚点（`workspace-write` 主防篡改边界）**：每次合法更新台账时，权威台账快照同步写入项目工作目录之外的 `SEAL_HOME/ledgers/<hash>.json`。在 DSH `workspace-write` 模式下，Agent 无法写入会话工作目录之外的 `SEAL_HOME/ledgers/` 与 `SEAL_HOME/vaults/`；即便同用户 Agent 读取了 `SEAL_HOME/keys/authorization.key` 并用合法 HMAC 重签篡改后的项目内 `ledger.json`，只要项目外锚点未被改写，`resolveLedger()` 仍会丢弃项目内伪造、恢复权威快照并在 C15 中阻断定稿。
- **授权记录带签名**：确认、接受、过目、人工跳过与覆盖标记，都带有用 `SEAL_HOME/keys/` 中的密钥计算的 HMAC（密钥不放在项目目录内）。签名无效的记录一律视为不存在，并在 C15 中报告。
- **草稿来源可查**：草稿的当前 SHA256 与 `drafts` 中记录的不一致，说明草稿被 Seal 以外的程序修改过，在 C15 中报告。
- **宿主边界诚实披露**：在当前单 OS 用户桌面宿主（DSH `0.2.2-rc.5`）下，`workspace-write` 只隔离项目外写而不隔离读；若用户主动切换至 `danger-full-access`（关闭写沙盒），同用户进程拥有本机完整读写权限，超出插件级隔离能力，须依赖上游宿主提供不暴露密钥字节的签名能力或操作系统级身份隔离。

## 五、检查目录（`seal_check`）

每项检查都是确定性计算。草稿阶段所有检查只报告、不阻断输出；“定稿”一列说明该项在定稿时是否阻断。

| 编号 | 检查 | 依据 | 定稿 |
| :--- | :--- | :--- | :--- |
| C01 | 文件合法性 | 子系统 2 第八节 | 阻断 |
| C02 | 未处理的疑似空白 | 当前草稿中仍能识别出、且没有有效跳过记录的提示 | 阻断 |
| C03 | Agent 跳过的空白 | 有效的 Agent 跳过记录中，人尚未过目的项 | 阻断，人可批量过目 |
| C04 | 待定项未确认 | 台账 `pending` 中状态为 `open` 的项 | 阻断 |
| C05 | 来源未核实的事实 | 引用了未核实的知识库字段、记录或图片（以“待核对”待定项出现），或 `_Seal_F_` 范围内文字与解析值不一致 | 阻断 |
| C06 | 原文改动 | 差异比较的 `modified`（含 `bracketText` 子类）、`deleted`，以及提示级的 `formatChanged` | 阻断，人逐项或按 `bracketText` 分组批量接受 |
| C07 | 内容丢失 | 差异比较的 `objectLost` | 阻断，人逐项接受 |
| C08 | 证据效期 | 草稿引用的证据在截标日已过期或即将过期；截标日或资料变化后重新计算 | 过期阻断，即将过期提示 |
| C09 | 主体一致 | 草稿全文出现 `forbiddenAffiliates` 中的名称；或出现格式像统一社会信用代码、与 `creditCode` 不同且不属于第三方资料的代码 | 阻断 |
| C10 | 待定标记可见 | 未确认待定项的 `_Seal_P_` 范围缺失，或范围内有文字没带黄标（子系统 2 第九节） | 阻断 |
| C11 | 日期合法 | 草稿中形如“YYYY年M月D日”的完整日期必须是合法的日历日期 | 阻断 |
| C12 | 招标要求覆盖 | `requirements.json` 存在时，必须响应的要求没有响应位置，或响应位置在草稿中不存在（文件损坏或无法解析亦报阻断；尚未建立 `requirements.json` 时计为 0） | 阻断，人可标记已覆盖 |
| C13 | 金额大小写一致 | 同一块或同一表格行内成对出现的中文大写金额与阿拉伯数字金额不相等（覆盖元/圆/角/分/整/正、万/亿、零、千分位逗号与常见标点边界；不依赖 `requirements.json`） | 阻断 |
| C14 | 要求引文核对 | `requirements.json` 存在时，其中的引文没有逐字出现在招标文件中（文件损坏或无法解析亦报阻断；尚未建立 `requirements.json` 时计为 0） | 阻断 |
| C15 | 草稿与台账完整 | 草稿被 Seal 以外的程序修改过，或台账中存在签名无效的授权记录（第四节） | 阻断 |
| C16 | 图片超出版面 | Seal 插入的图片尺寸超过[子系统 2](2-word-engine.md) 第十一节算出的所在位置可用宽高 | 阻断 |

- 报告按类别分组，每项给出编号、分册、地址、原文片段、原因与建议操作；每组有数量上限，并注明剩余数量。
- “原文是否被改动”由差异比较独立得出，不依赖编辑记录，也不依赖疑似空白提示。

## 六、定稿闸门与导出

- 条件：所有分册中，C01–C16 里标为“阻断”的项为零（已由人接受、确认、过目或标记的项不计；C08 仅“已过期”阻断，“即将过期”为提示）。`seal_check`、CLI `check` 与工作台的定稿就绪状态（`ready`）必须基于**全部分册、未截断的完整阻断计数**实时计算，不得因每组展示上限漏计后页阻断项，也不得写死常量。
- 导出只能由人在工作台触发：对每个分册执行定稿清理（子系统 2 第九节），写入 `final/<分册>.docx`，再对终稿执行 C01、C09、C10、C11、C16，全部通过才算导出成功。
- 导出不修改草稿。草稿此后若被修改，需要重新导出。

## 七、招标要求清单（`requirements.json`）

- 由 Agent 阅读招标文件后通过 `seal_requirements` 保存，Seal 在保存时校验格式与引文。
- 每条包括：`id`；`kind`（资格要求、评分项、实质性条款、废标条款、格式要求、递交要求）；`text`（Agent 的概括）；`quote`（原文片段）；`source`（招标文件路径与地址）；`mustRespond`（是否必须响应）；`points`（评分项分值，可选）；`responses`（草稿分册与地址列表）；`evidence`（证据记录 id 列表，可选）。
- 引文规则：去除空白差异与全角半角差异后，`quote` 必须出现在 `source` 指向的块或其前后 5 个块的文字中。
- 响应是否充分由 Agent 与人判断；Seal 只检查必须响应的要求是否有响应位置，以及这些位置是否存在。

## 八、`seal-bid` 操作手册（skill）

随插件发布的 skill，是 Agent 编写投标文件的流程指南，至少包括：

1. **读招标文件**：先看大纲，找出投标文件格式所在章节、投标文件组成与分册要求；再精读资格要求、评分标准、实质性条款与废标条款，保存要求清单。
2. **复制格式文件**：按投标文件组成选定范围，复制为分册。
3. **填写格式文件**：逐个处理疑似空白，企业主体与证照事实优先用引用；普通内容由 AI 直接高质量填充（不无故标黄），仅对报价、工期交期、质保、实质性偏离、签署日期与真实资料缺口等极少数敏感项声明待定；确认无需填写的提示，写明理由后跳过。
4. **撰写自拟章节**：按评分项组织目录，检索素材整合生成完整正式投标正文（正常白底，不对整章整段挂待定），仅对极少数真正待企业决策的数值或硬缺口用 `mark_pending` 局部标黄；不编造资质、业绩与数据。
5. **挂载证明材料**：只用有效的证据记录，第三方资料注明持证方。
6. **自检**：反复运行检查并修正 Agent 能处理的问题，渲染关键页面查看版式。
7. **交接**：向人总结完成情况、待拍板项、原文改动及原因、仍缺的资料。

手册还必须写明：草稿、台账与知识库只经 Seal 工具改动，不用脚本或其他程序改写 `draft/`、`ledger.json` 与知识库文件。

手册是可迭代的提示资产。改进 Agent 的表现时，优先修改手册与工具描述，并用真实招标文件评测效果。

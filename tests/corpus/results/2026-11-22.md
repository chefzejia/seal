## 5. 本轮发现并闭环修复的缺陷

1. **P0 大文档 XML 遍历 $O(P \times E^3)$ / $O(E^2)$ 性能缺陷（已修复：`6bfacea` → `0.1.345`）**
   - **现象**：在 63 页真实政府招标文件 `luoding-tax-property-2023`（`word/document.xml` 达 551–593 KB、21,784 个元素）上，`0.1.336` 单次 `seal_doc_read` 阻塞 158–177 秒并卡死宿主事件循环。
   - **根因**：`src/core/docx/pending-audit.ts` 在 `names.flatMap` 内部对每个待定项重复调用 `currentVisibleRunProperties`，且其内部与 `visible-surgery.ts`、`finalize-document.ts` 反复使用 `elements.find`/`some`/`indexOf` 做嵌套线性扫描；`check.ts` 亦在待定循环内重复解析 `bodyViewNodes`。
   - **第一性原理修复**：在 `src/core/docx/xml.ts` 增加共享 $O(E)$ 父子邻接表 `elementChildren(elements)`，全面线性化 `pending-audit.ts`、`visible-surgery.ts`、`seal-ranges.ts`、`finalize-document.ts` 并消除超长 run 的 `push(...Array)` 栈溢出风险；在 `check.ts` 惰性复用 `bodyViewNodes`。
   - **回归与复测**：新增 `tests/word-scale-performance.test.ts`（1,500 段 / 13,664 元素 / 40 待定范围 < 1,500 ms + 150,000 字符单 run），2 项 `Broken by hand` 破坏验证红→绿；真实 `luoding` 593 KB 草稿 `sealRanges + auditSealPending` 从 **~158,000 ms 降至 110.31 ms（约 1,400–2,500× 加速）**；`gpt-auditor` `NO_ISSUES`。

2. **P0/P1 C13 中文金额词法误报与 `万/亿` 单位换算缺陷（已修复：`2e8fb7a` / `1a4d4a8` / `588b7e3` → `0.1.356`）**
   - **现象**：在 `sccc-property-2022` 业绩表行（含年份 `2025`、日期 `2025-04-10` 与 `280万元(合成)`）上，`chinesePattern` 将单位名词 `万元` 误匹配为中文大写金额，且 `integer("万")` 算出 `0n`，造成无法消除的 C13 阻断误报；同时若同行确实成对出现 `280万元` 与 `叁佰万元整`，旧 `arabicPattern` 会忽略 `280万元` 导致漏报。
   - **第一性原理修复**：收紧 `chinesePattern` 与 `chineseMoneyCents` / `parseSmallSegment`，要求中文大写金额必须含有效大写数字、拒绝孤立量级名词（`万元`/`亿元`/`佰万元`）、拒绝连续非零数字（`壹贰元`）、零接单位（`壹佰零拾元`）及重复/递增单位（`壹佰贰仟元`、`壹佰贰佰元`）；扩展阿拉伯金额词法与纯 `BigInt` 精确十进制换算支持 `万/萬/亿/億 + 元/圆/圓`（屏蔽 `280万人`/`280万次`），并对带货币标记的超分位小数按统一精度比较而不截断。
   - **回归与复测**：在 `tests/bid-complete-checks.test.ts` 补充全套正负控与畸形语法用例，2 项 `Broken by hand` 红→绿；真实 `sccc` 的 C13 归零；异源 `gpt-auditor` 二轮审计分别抓出连续数字（P2）与递减单位（P1）边界，全部修复后最终审计 `NO_ISSUES`。

3. **P2 要求清单校验重复解析整篇文档（已修复：`2e8fb7a` → `0.1.356`）**
   - **现象**：`src/core/bid/requirements.ts` 的 `sourceCache`/`draftCache` 仅缓存 ZIP 字节映射，未缓存 `readableParagraphs(parts)`，在 66–83 条要求或 85 页标书上每次 `check` 耗时 4–8 秒。
   - **修复**：升级缓存为 `{ parts, paragraphs, addressSet, documentXml }`，每份文件仅解析一次；85 页 `golden` 单次 `check` 降至 1.29 秒，新增 100 条大文档性能回归测试（实测 `37.6 ms < 500 ms`）。

4. **Skill 实测引导收口（已修复：`6bfacea`）**
   - 在 `src/shells/dsh/seal-bid-skill.ts` 步骤 6 明确说明填写括号占位产生的 `bracketText`（C06）属人审批量接受预期项，避免 Agent 反复改写或尝试排查源码。

## 6. 观察到的 Agent 摩擦、剩余缺口与未覆盖范围

1. **已观察到的真实模型行为摩擦（非 Seal 故障，但影响人机协作效率）**：
   - `deepseek-v4.1-flash` 在长会话多步规划时偶发将 `<thinking>` 规划文本直接作为回复输出而不发起工具调用，导致回合提前结束（`zhengzhou`、`golden` 各需人工发送一次续推指令才继续执行）。
   - 大体量标书（如 63 页 `luoding`）产生较多需跳过的无关空白（`C03 = 376`），目前右栏支持「过目本类全部」批处理，后续可考虑按章节/表格进一步折叠以降低人工逐页浏览成本。
2. **已知微瑕（不阻断功能，记入后续打磨）**：
   - 终稿清理已移除全部 `_Seal_*` 书签及全部非空可见黄标（`nonEmptyYellow = 0`，LibreOffice 渲染零黄标），但 XML 中仍残留若干零长度空壳 `<w:r><w:rPr><w:highlight w:val="yellow"/></w:rPr><w:t xml:space="preserve"></w:t></w:r>`；虽不可见，后续可在 `finalize-document.ts` 顺手剔除零长度空壳高亮属性以令 XML 更洁净。
3. **本轮未覆盖范围（诚实披露）**：
   - **Microsoft Word / WPS 本机渲染**：本轮全部视觉验收均基于 LibreOffice Writer + 沙盒中文字形配置完成，未在 Windows/macOS 原生 Microsoft Word 或 WPS 客户端逐页核对排版差异。
   - **纯 PDF 招标文件**：`forestry-construction-2024`（161 页工程招标 PDF）仅作语料对照与字节校验；Seal 当前不从 PDF 逆向重建 Word 格式模板。
   - **宿主安全边界前提**：沿用单用户桌面三层信任模型（见 `docs/ARCHITECTURE.md` 决定 7）——DSH `0.2.2-rc.5` 的 `workspace-write` 沙盒仅限制会话 `cwd` 之外的**写入**（保护项目外权威锚点与知识库），不提供同 OS 用户跨路径**读隔离**；用户主动切换 `danger-full-access` 亦不在插件级隔离承诺内。
   - **非招投标场景包与真实商业签章**：通用文档/知识库/闸门底座已保持领域中立，但其他传统 Office 交付场景包暂未展开；真实项目的商业报价、工期、质保、偏离与最终签字盖章仍必须由人在工作台与纸面/电子签章环节亲自拍板。
